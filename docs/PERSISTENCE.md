# Persistence

How the Room schema in `:core:data` is versioned, and the assumptions any consumer of it - analytics, backup, import/export - is allowed to rely on.

## Where the schema lives

| Artifact | Path |
| --- | --- |
| Entities | `core/data/src/main/kotlin/com/titan/core/data/db/entity/` |
| DAOs | `core/data/src/main/kotlin/com/titan/core/data/db/dao/` |
| Database + migrations | `core/data/src/main/kotlin/com/titan/core/data/db/TitanDatabase.kt` |
| Reference data + catalogue seeding | `core/data/src/main/kotlin/com/titan/core/data/db/DatabaseSeed.kt` |
| Generated seed assets | `core/data/src/main/assets/seed/` |
| Seed generator | `tools/seed/generate_seed.py` (`make seed`) |
| Exported schema JSON | `core/data/schemas/com.titan.core.data.db.TitanDatabase/<version>.json` |
| Migration + DAO tests | `core/data/src/test/kotlin/com/titan/core/data/db/` |

KSP exports one JSON file per schema version (`room.schemaLocation` in `core/data/build.gradle.kts`). Those files are **committed** and wired in as `test`/`androidTest` assets, which is what lets the migration harness build a historical database from its own spec.
Deleting or hand-editing a released version's JSON removes the only record of what shipped.

## Migration strategy

The database is deliberately **not** built with `fallbackToDestructiveMigration`. A version that has no path to the current schema throws at startup rather than silently wiping a user's training history - offline-first means the device is the only copy.

### Checklist for a schema change

1. Change the entities.
2. Bump `version` in `@Database` (`TitanDatabase.kt`).
3. Add a `Migration` covering the bump to `TitanDatabase.MIGRATIONS`.
4. Build once so KSP exports `schemas/<new version>.json`, and commit it.
5. Add a `MigrationFixture` for the version you migrate *from* in `DatabaseMigrationTest`: it seeds rows through raw SQL at the old version and asserts they survive the upgrade.

**While the app is pre-release, version 1 is amended in place instead.** Nothing is installed that has to be carried forward, so an entity added today re-exports `1.json` over the committed one - steps 2, 3 and 5 have nothing to do, because there is no released version below the current one to migrate from. The cost is paid by whoever already has a build on their phone: the identity hash in `1.json` changes, `MIGRATIONS` is empty and there is no destructive fallback, so the next launch throws `Room cannot verify the data integrity` until the app is reinstalled or its data cleared. That trade ends at the first release - from the version that ships to a user onwards, `1.json` is a record of what shipped and the five steps above are the only way to change the schema.

`DatabaseMigrationTest` enforces every step - it reads the current version and the exported schema list at runtime, so it never needs editing for a new version, only a fixture:

| Test | Fails when |
| --- | --- |
| `every schema version up to the current one is exported` | step 4 was skipped |
| `the current schema matches its exported spec` | entities drifted from the committed JSON |
| `migrations form an unbroken path from version 1 to the current version` | step 3 was skipped, or a gap between two bumps |
| `every exported version migrates up to the current schema` | a migration produces a schema Room does not accept |
| `every migration preserves the data seeded at its start version` | step 5 was skipped, or a migration loses data |
| `opening a database at an unmigrated version fails instead of wiping it` | a destructive fallback gets added |

### Writing the migration itself

- Foreign keys are **not enforced inside the migration transaction**: `PRAGMA foreign_keys = ON` is applied by `TitanDatabase.foreignKeysCallback` in `onOpen`, which Room runs *after* migrations. A migration that rebuilds a table (SQLite cannot alter constraints in place) should finish with `PRAGMA foreign_key_check` to prove it did not orphan any child row.
- `DatabaseSeed` runs from `seedCallback.onCreate`, which fires **only on a fresh install**. New reference data (a muscle group, a system tag) must therefore be inserted by the migration *and* present in the seed, otherwise existing installs never get it. Use `INSERT OR IGNORE` in both, keyed on the unique `name`.
- Version 1 has not shipped yet, so it may still be edited in place with the JSON regenerated - which is how `workout_session.name`, the two `superset_group` columns, `workout_template.category` and `body_measurement`'s five measurement columns were added, rather than as a v2 with a migration nothing would ever have run. Once a version is released, it is frozen: correct it with a new version, never by editing it. Editing a version some *other* version migrates from is off the table from the first bump either way - `MIGRATION_FIXTURES` seeds that version's tables by raw SQL, and rewriting the schema underneath it turns a data-loss test into a syntax error.

## Seed data

The baseline exercise library is **generated, not hand-written**. `tools/seed/generate_seed.py` reads the public-domain [`yuhonas/free-exercise-db`](https://github.com/yuhonas/free-exercise-db) dataset, pinned in `tools/seed/source.lock` by commit and by the sha256 of that commit's tarball, and emits two assets:

| Asset | Contents |
| --- | --- |
| `core/data/src/main/assets/seed/exercises.sql` | 17 muscle groups, 9 system tags, 873 exercises, 2 574 muscle links, 1 722 tag links |
| `core/data/src/main/assets/seed/images/*.webp` | One 400 px photo per exercise, ~8 MB total, referenced by `exercise.icon` |

| Command | Effect |
| --- | --- |
| `make seed` | Regenerate from the pinned commit |
| `make seed-update` | Re-pin `source.lock` to upstream HEAD, then regenerate |
| `make seed-rehash` | Pin the tarball sha256 of the commit already in `source.lock` (after Renovate moves it), then regenerate |
| `make seed-check` | Fail if the committed assets are stale (runs in CI) |
| `make seed-test` | Run the generator's own tests, `tools/seed/test_generate_seed.py` (runs in CI) |
| `make seed-deps` | Install the hash-pinned Pillow from `tools/seed/requirements.txt` |

**The generator trusts nothing it reads.** The tarball's sha256 is checked on every run, whether it was just downloaded or came from `tools/seed/.cache`, and a download is cached only once it matches. Pinning (`seed-update`, `seed-rehash`) also asks GitHub whether the commit is in upstream `main`'s history: GitHub shares objects across a fork network, so codeload serves a fork-only commit under the upstream name. A commit that is not 40 lowercase hex characters, an upstream exercise id outside `[A-Za-z0-9_-]+`, and a C0 control character in upstream text each stop the run before anything is written.

**`make seed-check` compares bytes, not names.** It regenerates the SQL and re-encodes every image in memory, and fails on any image that differs, is missing, or is not a regular file, and on any file in `images/` the generator would not write, whatever its extension. The images are reproducible only with the encoder that made them, so the check needs the Pillow pinned in `tools/seed/requirements.txt` (its wheels bundle libwebp): CI installs it with `--require-hashes`, and locally `make seed-deps` does the same in a CPython 3.14 virtualenv, the series the hashes cover. A wheel built for another platform may encode differently, so CI's Linux run is the one that decides.

A Renovate PR that moves the commit leaves `tarball_sha256` behind, so `make seed` and the CI check fail on it with a sha256 mismatch until someone runs `make seed-rehash` on the branch and commits the result. Renovate cannot compute that digest itself. It raises that PR only once it is approved on the Dependency Dashboard: a branch digest has no release timestamp for `minimumReleaseAge` to wait on.

`exercises.sql` is replayed verbatim by `DatabaseSeed.insertInto`. Its format is deliberately parser-free - **every line is blank, a `--` comment, or one complete statement** - which is why instruction paragraphs are re-joined with `char(10)` concatenation instead of embedding raw newlines. Anything editing the generator must preserve that invariant. Every statement is `INSERT OR IGNORE`, so a replay over a populated database is a no-op; `DatabaseSeedTest` asserts this.

### Default templates

The seed has a second step after the catalogue: `DatabaseSeed.insertDefaultTemplates` writes the default templates (#213) into `workout_template`, `template_exercise` and `template_set`, in the same transaction as `exercises.sql`. They are defined in Kotlin, in `core/data/.../db/DefaultTemplates.kt`, not in a generated SQL file, for two reasons. **The names are string resources**, read in the device's language when the database is created, so a French phone starts with *Jambes* rather than *Legs*. **Exercises are referenced by the catalogue's natural key** - name and equipment type, on a seeded row with no machine brand - and resolved when the rows are written. They are never referenced by id, because the seed's ids are positional and move on every regeneration (see below). The rows are written through the support database because `onCreate` has no DAO, and they are numbered by `TemplateExerciseMapper`, the same code the template repository writes with.

Once written they are **ordinary templates**. No column marks them, so the user renames, edits and deletes them like any template, and export, import, `observeFootprint` and the widget treat them as user rows. `icon` stays NULL, as on every template the editor writes.

**This step is not idempotent, and must not be.** `workout_template.name` has no unique index, so a second run duplicates every default. It runs exactly where `DatabaseSeed.insertInto` runs: `onCreate`, and after `clearAllTables` in "Delete all data", where the wipe leaves the defaults back as a fresh install has them. It never runs on open, and never during an import. A default the user deleted stays deleted across restarts and restores; Settings › Workout › *Restore default templates* (`RestoreDefaultTemplatesUseCase`, over `DefaultTemplateCatalogue`) puts back the ones whose name, in any language the app ships, no template carries, under their name in the current language. Matching every language is what keeps a change of phone language from making every seeded default look deleted.

A default whose exercises do not all resolve is **skipped with a log line** rather than failing the seed: an unresolvable name is a build mistake, and a build mistake must not stop first launch. `DatabaseSeedTest` resolves every reference against the real catalogue and fails on any miss, so the skip path does not run in a shipped build.

Exercise, muscle-group and tag ids are **written explicitly** by the generated SQL rather than autoincremented, because the link rows have to reference them. They therefore follow the ordering of `MUSCLE_GROUPS` / `SYSTEM_TAGS` in the generator and the upstream slug sort for exercises: reordering either constant renumbers rows, so the regenerated SQL must be committed with the change.

### Field mapping

| Column | Upstream field | Note |
| --- | --- | --- |
| `name`, `instructions` | `name`, `instructions[]` | Paragraphs joined with `\n` |
| `exercise_type` | `category` | `ExerciseType` is a *logging mode*: every barbell-shaped discipline folds into `STRENGTH`, `cardio` → `ENDURANCE`, `stretching` → `ISOMETRIC` |
| `discipline` | `category` | 1:1. Keeps what the fold above destroys - five disciplines share `exercise_type = STRENGTH`, so neither column derives the other |
| `equipment_type` | `equipment` | Never NULL - upstream's `other` and a missing value both become `OTHER`, because a NULL would defeat the unique index (SQLite treats NULLs as distinct) |
| `mechanic_type`, `difficulty_level` | `mechanic`, `level` | Direct, nullable |
| `is_unilateral` | *derived* | Inferred from name markers (`One-Arm`, `Single-Leg`, `Alternating`, …); no marker means the `false` default, never a guess |
| `icon` | `images[0]` | Asset-relative path to the bundled WebP |
| `exercise_muscle_group` | `primaryMuscles`, `secondaryMuscles` | Exactly one `is_primary` row per exercise, enforced by the generator and by `DatabaseSeedTest` |
| `exercise_tag` | `force`, `mechanic`, `category`, `name` | Links to the seeded `PUSH`/`PULL`/`STATIC` and `COMPOUND`/`ISOLATION` system tags; `DYNAMIC` for the stretches and plyometrics that travel (#214); `SPEED` for the cardio rides, rows and skates and `SWIM` for the swims, read off the name - how a best pace is shown (#225) |

Every upstream field is imported except the second of each exercise's two photos. `machine_brand`, `default_rest` and `notes` stay NULL rather than being fabricated: all three belong to the user, not the catalogue.

`notes` and `instructions` are easy to confuse and must not be. **`instructions` is the canonical how-to** - imperative, second-person, seeded from upstream ("Stand up with your torso upright while holding a barbell…"). **`notes` is whatever the user writes about the exercise** and is never seeded. A third-person summary of a movement belongs in neither: the dataset has no such field, and duplicating `instructions` under a second name is what the old `description` column invited before it was renamed.

## Storage assumptions

Physical units are integers - no floating point anywhere in the schema, so values round-trip through JSON exactly.

| Concept | Unit | Columns |
| --- | --- | --- |
| Weight | milligrams | `workout_set.weight`, `personal_record.weight`, `personal_record.estimated_1rm`, `template_set.weight`, `body_measurement.weight` |
| Distance | centimeters | `workout_set.distance`, `personal_record.distance`, `template_set.distance` |
| Circumference | millimeters | `body_measurement.chest`, `.waist`, `.arm`, `.thigh` |
| Body fat | percent x 10, range 1-1000 | `body_measurement.body_fat` |
| Duration and rest | seconds | `workout_set.duration`, `workout_set.rest_after`, `personal_record.duration`, `template_set.duration`, `exercise.default_rest` |
| RPE | RPE x 10, range 10-100 | `workout_set.rpe` |
| Timestamps | epoch milliseconds, UTC | every `*_at` column |
| Booleans | INTEGER 0/1 | `is_completed`, `is_in_progress`, `is_primary`, `is_system`, `is_custom`, `is_unilateral` |

Other invariants:

- **Enum-like text columns** (`exercise_type`, `discipline`, `equipment_type`, `mechanic_type`, `difficulty_level`, `set_type` on both `workout_set` and `template_set`, `pr_type`, `workout_template.category`) hold uppercase identifiers validated by the domain layer. Room cannot express SQL `CHECK` constraints, so the database will accept anything - an importer must validate them itself.
- **`workout_set.completed_at` is NOT NULL** even for a set that is not finished; callers write `0` as a placeholder and flag it with `is_completed = 0`. Analytics filter on `is_completed = 1`, so placeholders never reach an aggregate - but a row with `is_completed = 1` and `completed_at = 0` would be counted at epoch 1970. A set that *was* performed and has since been un-ticked - `MarkSetCompletedUseCase`, the way back from a tick pressed by accident - keeps the timestamp it was performed at and only clears the flag: it is out of every aggregate either way, and clearing the column would leave the row unable to say when it had been done if the tick goes back on.
- **`workout_session.completed_at` is nullable**; a session in progress is identified by `is_in_progress = 1`, and resume picks the highest `last_active_at`.
- **`workout_session.name` is nullable, and NULL is not the same as `''`.** A session started from a template copies the template's name at apply time - `ApplyTemplateUseCase` returns it on the plan and `StartSessionUseCase` writes it - so renaming the template afterwards does not retitle workouts already logged under the old name, and `template_id` is a record of provenance rather than the source of the title. A session started empty has NULL, meaning genuinely unnamed, which is what the UI's date-derived fallback keys off; a `NOT NULL DEFAULT ''` would make "unnamed" and "named with an empty string" the same row. `WorkoutSession.normalizeName` trims the name it is handed and collapses blank to NULL, and it is the one implementation of that rule — the name is set in three places (`StartSessionUseCase` before the session exists, `RenameSessionUseCase` during it and after it), so the app never writes `''` - but nothing in the *schema* holds that, and an importer or a restore writing directly to the table can, so a consumer that treats blank as unnamed should test for it as well.
- **`session_exercise.superset_group` and `template_exercise.superset_group` are nullable ordinals, and NULL means "not in a superset".** Exercises of one session (or one template) sharing a non-null value are performed back to back as one superset, ordered by their `position`; the value itself is an ordinal within that one list, numbered densely from 0 in position order, which is what a screen renders as the `A` in `SS A1`. It means nothing across sessions and is **not stable across an edit** - nothing may store a group id and expect to find the same exercises under it later. Three rules hold it together and *none of them is in the schema*: a group has at least two members, a group's members occupy consecutive positions, and a rest is attributed after the last member rather than between members. `Supersets` in `:core:domain` is where they live and `TemplateError.InvalidSuperset` is what refuses a template that breaks them, so - as with the enum-like columns and the set bounds - an importer or a restore writing to these tables directly has to check them itself. A group left with one member is not an error but a non-superset: the write path dissolves it back to NULL rather than refusing the list.
- **`workout_template.category` is nullable, and NULL is not `GENERAL`.** It holds one `TemplateCategory` name - the chip a template row shows - and NULL means the template was never given one, which a screen renders as no chip rather than as a chip reading "General". One column rather than a `template_tag` join mirroring `exercise_tag`: a template carries exactly one category, so the join would buy a many-to-many nothing asks for, put a join on the read that lists every template, and add seeded reference rows for an importer to resolve by name. As with every other enum-like column the value is unconstrained by the schema, and a name this build does not know reads back as NULL rather than making the row unreadable.
- **What a template plans lives in `template_set`, one row per set.** A `template_exercise` says which movement and in what order; the sets under it say what to do - `set_type`, `reps`, `weight`, and for a timed exercise `duration` and `distance` - numbered from 1 and contiguous within one exercise, with `(template_exercise_id, set_number)` unique. It replaced three columns on `template_exercise` (`default_sets`, `default_reps`, `default_weight`) that could only describe *n identical sets*, which is not how anybody trains: the warm-up, the working sets and the drop set were unrepresentable, so the plan a user wrote down was never the workout they did. Unlike `workout_set` the numbering *is* indexed unique, because a template's body is only ever replaced wholesale (`WorkoutTemplateDao.updateWithExercises`) and there is no renumbering pass that would have to park rows out of the way. A set carries no `rpe` - a plan does not record how hard a set felt - and neither it nor `template_exercise` carries a rest: the workout's timer runs the exercise's own `exercise.default_rest`, or the user's setting where it has none, whatever the template says (`RestDurations` in `:core:domain`), so a rest stored on the plan would be a figure nothing runs. An exercise with no `template_set` rows is legal and means the line plans a movement and leaves its sets to the day.
- **Applying a template writes its plan as real `workout_set` rows with `is_completed = 0`** - the planned-but-unperformed state the bullet above describes. `StartPlannedSessionUseCase` copies each `template_set` onto the session in order, stamping `completed_at = 0`, so a four-set template opens a four-set workout the lifter ticks off rather than one empty row they retype. The rows are ordinary sets from that moment on: the session owns them, editing or deleting the template afterwards does not reach them, and `session_exercise.template_exercise_id` remains the only link back. Ticking one off stamps `completed_at` for the first time, which is the one case `MarkSetCompletedUseCase` writes that column.
- **A template's estimated duration is derived on read and has no column, deliberately.** `TemplateDuration` in `:core:domain` computes it from the template's exercises - per exercise, `30 s` of work per set (or the set's own `duration`, where the plan gives one - a 30-minute ride is thirty minutes, not thirty seconds) plus `sets x` the rest the workout's timer will run after it (`RestDurations`: the exercise's `default_rest`, falling back to the user's default rest), minus the final rest of the workout, with a superset's members contributing rest only after the last of them, where `sets` is how many `template_set` rows the exercise has. A stored estimate would be wrong the moment an exercise, a set or a rest changed, and keeping it true would mean a second write on every edit whose only job is to restate the rows; nothing in an export should carry one either, since an importer can compute it from the rows it already has. An exercise that plans no sets is not performed and costs nothing. The formula is a pacing figure for a list row, not a measurement - what a session actually took is `workout_session.created_at` to `completed_at`.
- **`body_measurement` is one dated entry per trip to the scale and the tape, and every measurement on it is nullable - `weight` included.** It replaced `body_weight_log`, which held a weight and nothing else. A user weighs themselves and reaches for the tape in the same two minutes, and the body screen logs that as one entry pre-filled from the last, so a companion table would have turned one write into two and left the history screen two lists to interleave by timestamp. The case that would have justified splitting them - measurements logged genuinely apart from weight - is served by the optionality instead: an entry may carry a waist and no weight as readily as a weight and nothing else, and nothing in the schema makes one column the price of writing another. What the schema does *not* hold is that an entry records anything at all: `BodyMeasurementValidator` in `:core:domain` is what refuses an all-null row (and bounds the figures, as `SetValidator` does for a set), so an importer or a restore writing here directly has to check it itself. `created_at` is when the measurement was **taken**, not when it was typed, which is what both queries order by - an entry logged this evening for this morning's weigh-in belongs where it falls in the series.
- **Lean mass is derived on read and has no column, for the same reason a template's duration has none.** `BodyMeasurement.leanMass` is `weight x (1000 - body_fat) / 1000`, a pure function of two fields on the same row: a stored copy could only agree with them or be stale, and keeping it true would mean a second write whose whole job is to restate the row. Nothing in an export should carry one either. The arithmetic is integer throughout - tenths of a percent *are* thousandths of the whole, so `body_fat` divides by 1000 with no scaling - and the truncation costs at most a milligram on a figure measured in tens of kilograms. The weight is split into whole grams and the milligrams left over before it is scaled, so the product never leaves a 64-bit integer whatever weight a restored row holds. A `body_fat` outside 0-1000 - a corrupt row, since `BodyMeasurementValidator` bounds it to 1-1000 - yields no lean mass at all, the way an out-of-range RPE reads as not recorded, rather than a figure outside `0..weight` or a clamped fiction.
- **`workout_set` value bounds** - `reps` in 1-10,000, `weight` in 0-10 t (0-10,000,000,000 mg), `duration` in 1-864,000 s (10 days), `distance` in 0-10,000 km (0-1,000,000,000 cm), `rest_after` at least 0 - are checked by `SetValidator` in the domain layer, and nothing in the schema holds them. `SetValidator` is a check a caller runs, not a gate the write path forces it through: a use case has to call it first or the bounds simply do not hold for that row. A restore deliberately does not call it (see [export-schema.md](export-schema.md#what-is-deliberately-not-refused)), so every reader has to survive a row outside the bounds: the aggregates sum in a way that cannot overflow (see [Analytics assumptions](#analytics-assumptions)), and the next-load engine judges only sets inside them. A NULL dimension is legal and is not a bound violation. The ceilings catch a stray digit or a unit mix-up; they are not meant to be plausible limits, so multi-day ultras and sled pushes fit under them. The widest set they admit is 1e14 milligram-reps of volume, two orders of magnitude inside a signed 64-bit range over a 100-set session.
- **`workout_set.set_number` is contiguous from 1 within one `session_exercise`, and nothing in the schema holds that either.** It is read as much as stored - it is the `3` in "set 3 of 4", it orders the table under an exercise, and a previous-performance lookup lines two sessions up on it - so a gap in it is a set the user is told they performed and cannot find. `LogSetUseCase` numbers a new set one past the highest in use, and `DeleteSetUseCase` closes the gap a deletion leaves by renumbering the survivors in one write (`SessionRepository.updateSets`); `RestoreSetUseCase` opens it again when an undo puts a set back at the number it had. There is deliberately **no** unique index on `(session_exercise_id, set_number)`, unlike `session_exercise`'s positions: a renumbering would then have to park its rows out of the way first, which buys nothing here, since the invariant a reader depends on is denseness rather than uniqueness and no index can express that. An importer or a restore writing sets directly has to number them itself.
- **Which dimensions a set must fill in depends on `exercise.exercise_type`**, so it cannot be read off the `workout_set` row alone: a `STRENGTH` set records `reps`, an `ENDURANCE` set a `duration` with `distance` optional, an `ISOMETRIC` set a `duration`. `SetValidator` only applies this to rows with `is_completed = 1` - a planned set is stored with its dimensions still empty. Filling the *other* dimensions is never refused; a timed squat set and a loaded carry are both legitimate.
- **`user_progress` holds exactly one row, and the schema is what says so.** There is no `user_id` column and no user table - the app is single-user and local-first, so such a column would hold one value forever and invite a join that can never be written. The primary key is fixed at 1 with a `CHECK (id = 1)` beside it, which is a stronger statement than a convention every caller has to remember. Room cannot express a check constraint in `@Entity`, so the table is dropped and re-created from `UserProgressEntity.CREATE_TABLE_SQL` by `TitanDatabase.singleRowProgressCallback` in `onCreate`: **anything that opens this database must register that callback, tests included**, or the constraint is simply not there. There is no row at all until the first XP award or finished session - "nothing banked yet" is a state a surface may render differently from a user who has trained and holds no XP, and `UserProgressDao.mutate` supplies the empty row on the write side rather than seeding one at create time.
- **`user_progress.current_level` is stored rather than derived, and is only ever written from `XpCalculator`'s curve.** A level is arithmetic over the total, so a column can only agree with it or be stale; it is kept because a level-up has to be reported by the write that caused it, and a read-back cannot say which award crossed the threshold. Both the level before an award and the level after come from the curve applied to the totals either side of the delta, never from the column, which was written by whatever curve was in force when it was last touched - reusing it would make the first award after a retune of the curve report a level-up, or a level *drop*, the user did not earn. The total itself is held to `0` through `XpCalculator.MAX_TOTAL_XP` (10^15), past which the curve overflows an `Int`; a restored row outside that, or with a level outside what it buys, is repaired on its way in and again by every reader (`UserProgressMapper.repaired`, listed in [export-schema.md](export-schema.md#what-is-repaired-rather-than-refused)).
- **`user_progress.last_counted_at` is the last session counted towards the streak, and `week_sessions` / `week_goal_met` describe the week it falls in.** A session finished at or before `last_counted_at` counts nothing, which is what makes a re-run of the cascade or a backfilled session harmless - `StreakCalculator` measures from it and says the rest. `week_goal_met` is stored rather than derived from `week_sessions` because the weekly goal is a setting that can change mid-week, and what counts is the goal in force when each session was finished. An importer that rewrote any of the three would quietly move every subsequent streak decision.
- **`achievement` is keyed by the domain's own string id, and the catalogue is not a table.** Which milestones exist is data in `:core:domain` (`Achievements`), so adding one is a line there and no schema change; a row here means one was actually reached. The write is `INSERT OR IGNORE` on that key, so unlocking twice leaves one row carrying the moment it was **first** earned, and `unlocked_at` is the finishing session's own timestamp rather than when the row was written. A row whose `achievement_id` this build does not recognise is an unlock from a newer version, not a corrupt row: a restore must preserve it. The one exception is the session-based streak's two milestones, `seven_day_streak` and `thirty_day_streak`, which a file from before the weekly streak can hold and `WeeklyStreakUpgrade` drops on the way in, along with that file's streak counts; it also recomputes that file's `current_level` from `total_xp`, which the old XP curve priced at a sixth of today's cost per level.
- **`user_progress.protection_remaining` is what is left of *a month's* streak-protection allowance, and the month it belongs to is `protection_period`.** One a month, spent automatically when a week that fell short of the weekly goal would otherwise break a streak worth keeping - `StreakCalculator.advance` decides, and the decision, the streak write and the spend are one transaction, because a scarce allowance read twice before either write is one two callers would both be told they may spend. The month is stored as `YYYY-MM` text and the rollover is **lazy**: nothing refills the column on the first of the month, because nothing can spend from it except a finished session and every write applies the rollover first. The consequence for a reader is written into `GamificationRepository.observeStreak` - a state read in a month the user has not trained in still carries the previous month's remainder, and a surface that renders the count applies `StreakProtection.replenishedFor` for the month it is drawing in. `protection_consumed_at` is a record of the last spend, carried through a backup; nothing decides anything from it, and the guarantee that one short week cannot be paid for twice rests on `last_counted_at` advancing, exactly as counting each session once already required.
- **`session_xp_claim` is a marker table with no payload** - one row per session whose XP has been paid for, and the row's existence is the whole value. It exists because XP is the one part of the post-session cascade that is not idempotent by construction: PR detection compares strictly better, an already-counted session leaves the streak unchanged, an unlock is insert-if-absent, and `addXp` banks whatever it is handed. The claim is taken before the awards, which chooses under-paying over double-paying. It cascades with its session, and a restore that drops these rows re-opens the double-pay window for every session a cascade later re-runs, so they belong in an export beside the sessions they fence.
- **`session_loot_claim` is the same marker table again, over the other un-idempotent step of that cascade** - one row per session whose drop table has been rolled, keyed and cascading exactly as `session_xp_claim` is. XP is not the only step a re-entry could repeat: a roll is a decision taken from a random source, so re-running a processed session would hand out a second collectible. Everywhere else in the cascade the write is its own fence - an unlock and a quest completion are both `INSERT OR IGNORE` over a natural key - but the inventory cannot be, because the same collectible dropping **again** is a normal thing to hold and a unique index there would refuse the second legitimate drop as readily as the duplicate one. So the fence sits over the *roll*, one table up, and is taken **before** it: a torn run that drops nothing, rather than a crash-recovery boot that drops on every pass. It is spent whether or not the roll paid out, because what it fences is the roll and four rolls in five pay out nothing - a claim that only closed on a payout would let a re-entered cascade roll until one landed. Two claim tables rather than one shared "the cascade ran" row, because they fence independent steps: a run that died after the awards and before the roll must still be able to roll on re-entry. Like the XP claim, a restore that drops these rows re-opens the double-roll window for every session a cascade later re-runs.
- **`collected_item` is an inventory rather than a set, and its own rowid is what says so.** Which collectibles exist is data in `:core:domain` (`#107`) rather than a table, the same call `achievement` makes; what differs is multiplicity. An unlock happens once, so `achievement` keys on the domain id and writes `INSERT OR IGNORE`. A collectible can drop **again** - next week, or twice in one month - and a user who has pulled three of something holds three of them, so every drop is a plain insert and a second one is a second row. Keying on `collectible_id` would quietly collapse the inventory back into a set. Nothing here is idempotent and nothing is meant to be: what stops a re-entered cascade rolling twice is a fence over the *roll* - `session_loot_claim`, the bullet above - not a unique index over its result, which could only refuse the second legitimate drop as well. `acquired_at` is the triggering event's own timestamp rather than when the row was written, and it is indexed because the one read orders by it and takes the newest few, over a table that grows for the life of an install. `source` is the stable key of what caused the drop, held on the row rather than looked up from the collectible so that a build which does not recognise the collectible can still say where its drop came from - and, like `collectible_id`, it is **not** validated against anything this build knows: a row naming either from a newer version is a drop, not a corrupt row, so a restore must preserve it and read it back as it was written. That is `achievement`'s rule, verbatim, applied to both columns.

### Identity and uniqueness

| Table | Natural key | Note |
| --- | --- | --- |
| `exercise` | `(name, equipment_type, machine_brand)` unique | Keeps PRs separate per machine brand. SQLite treats NULLs as distinct, so rows with a NULL brand do **not** collide with each other |
| `muscle_group` | `name` unique | 17 seeded values |
| `tag` | `name` unique | 9 seeded system tags, plus user tags |
| `session_exercise` | `(session_id, position)` unique | Reordering must not transiently duplicate a position - `SessionExerciseDao.rewriteLayout` parks every row it is about to move at a negative position first, in one transaction, so no intermediate state has two exercises on one |
| `template_exercise` | `(template_id, position)` unique | Same |
| `template_set` | `(template_exercise_id, set_number)` unique | Numbered from 1. Unique here where `workout_set` is not, because a template's body is replaced wholesale rather than renumbered in place |
| `workout_set` | none | `(session_exercise_id, set_number)` is dense within one exercise but is **not** indexed unique - the numbering is the use cases' invariant, per the bullet above, and denseness is what a reader needs |
| `user_progress` | `id`, pinned to 1 | A single-row table; the `CHECK` that pins it is applied by a callback, not by Room - see the bullet above |
| `achievement` | `achievement_id` primary key | The domain's stable milestone id, so the uniqueness that makes an unlock happen once is the key itself |
| `session_xp_claim` | `session_id` primary key | One claim per session |
| `session_loot_claim` | `session_id` primary key | One roll per session, over the same key and for the same reason |
| `collected_item` | none - `id` is the whole identity | Deliberately: the same collectible drops more than once and each drop is its own row |

Every `id` column is an autogenerated local rowid, apart from `user_progress.id`, which is a constant, and `achievement`, `session_xp_claim` and `session_loot_claim`, which are keyed by a domain id and a session id respectively - `collected_item` is a rowid like the rest. **Ids are not portable across devices or exports** - anything that has to match rows across installs (import/export, backup restore, a future sync) must match on the natural key above and remap ids, never trust an exported id.

**Ids are not unique over time either.** The tables use `AUTOINCREMENT`, which never hands out a number below the largest a table has held, but a restore writes back ids this device has used before, and "Delete all data" clears `sqlite_sequence` with the rows, so numbering starts from 1 again as on a fresh install (`LocalDataRepositoryImpl.wipe`). A counter kept through a wipe would carry the old history's numbering into the new one, and an id near `Long.MAX_VALUE` left behind by a restore from before such ids were refused would make every later insert fail with `SQLITE_FULL`. A restore does not reset the counters: its wipe and inserts are one transaction, and the counters end at the larger of the file's ids and the ones this device had used. So nothing outside the database may name a row by its id alone and expect it to be the same row later. Anything that reaches the app from outside the process naming a session - the rest-expiry and idle alarms, and the notification buttons - carries the row's `created_at` beside the id (`SessionRef`), and is refused when the row under that id was created at another time.

## Analytics assumptions

The aggregates in `WorkoutSetDao`, `WorkoutSessionDao` and `PersonalRecordDao` run in SQLite so results scale with the number of buckets, not the number of sets. They assume:

- **Volume = `weight x reps`**, in milligram-reps. A set missing `weight` or `reps` (cardio,
  holds) contributes 0 rather than dropping its bucket from the series.
- **Only completed sets count** (`is_completed = 1`).
- **Every sum is `CAST(TOTAL(...) AS INTEGER)`, never `SUM`.** SQLite's `SUM` over integers raises `integer overflow` once the total leaves a 64-bit integer, and fails the query with it, so one restored set past `SetValidator`'s bounds used to take down the History list, the Stats screen and the dashboard at every launch. `TOTAL` sums in floating point and cannot overflow; the cast brings the result back to an integer, held at the `Long` bounds. Below 2^53 every partial sum is exact, so an honest history sums to what `SUM` gave. `WorkoutSetDao` carries the argument at the class level, and `getTrainingMillis` does the same.
- **Weeks start Monday, UTC.** `getVolumeByWeek` derives the epoch day as `workout_session.completed_at / 86400000` and shifts by `+ 3` because epoch day 0 was a Thursday. There is no local-timezone or DST handling: a session logged late on a Sunday evening west of UTC lands in the following week's bucket. The arithmetic holds only from 1970 on, because SQLite's `/` and `%` truncate towards zero, so both weekly series leave a session finished before 1970 out of every bucket; the import refuses such a timestamp, and the stats screen never opens a period before 1970 either.
- **The week boundary has a domain twin too.** `getTrainingByWeek` repeats that arithmetic against `workout_session`, and `:core:domain`'s `TrainingWeek` states it a third time in `java.time` — the use cases have to know which weeks a period contains *before* any row is read, since a week nobody trained in produces no row and has to be drawn as a zero rather than skipped. `TrainingWeekParityTest` holds all three to one answer; if they drift, a week's training silently falls into a gap the domain then zeroes.
- **Day ranges are half-open** `[startEpochDay, endEpochDayExclusive)` and are expressed in epoch days, converted to milliseconds inside the query. Both weekly series are bounded at *both* ends, so a period-over-period comparison can ask for a window that stops; a range whose ends fall mid-week returns partial boundary buckets, which is why `VolumeTrendUseCase` snaps its period to Mondays before asking.
- **Consistency counts days, not sessions.** `getTrainingByWeek` returns `COUNT(DISTINCT completed_at / 86400000)` beside the raw `COUNT(*)`: two sessions finished on one day are one day trained. It counts only sessions that were *finished* — `is_in_progress = 0` and a non-null `completed_at`, which `FinishSessionUseCase` writes together — and buckets by when the session was closed out, not when it started. A discarded session is deleted rather than flagged, so there is no third state to filter.
- **The volume and consistency series share a row filter as well as a week boundary.** Both count only closed-out sessions, and both place a session in the week it was *finished* in — so `getVolumeByWeek` joins a set up to its session and buckets on `workout_session.completed_at`, not on the set's own stamp. Every week with volume in it therefore has a training day behind it, and a session that runs past midnight UTC lands wholly in one week. The cost is deliberate: a workout in progress contributes no volume to the chart until the user finishes it, so the current week's bar fills in at the end of a session rather than set by set. The alternative charts work with no training day behind it, and leaves an abandoned session's volume in the series for good. A session's own recap is unaffected — `getTotalsBySession` is per session and does not filter on session state, so a workout in progress still totals live on the screen showing it.
- **"Has the user ever trained?" is its own query.** `hasFinishedSession` is an `EXISTS` over the same filter with no window on it. No period-bounded series can answer it: an empty window reads identically for somebody who has never trained and somebody who stopped, and the comparison period separates the two only while the lapse is shorter than twice the window. `VolumeTrend`/`ConsistencyTrend` carry it as `hasEverTrained` so a screen can tell a first run from a break — the difference between a "log your first session" prompt and an empty chart for a lifter of three years.
- **Muscle attribution is per link, not per set.** `getVolumeByMuscleGroup` fans a set out across `exercise_muscle_group`, so `total_volume` credits the full volume to every linked group and intentionally sums to more than the session total. `weighted_volume` applies 100% to a primary link and 50% to a secondary one, with integer division truncating the halved value.
- **`weighted_volume` has a domain twin.** `MuscleVolumeCalculator` in `:core:domain` applies the identical rule to sets already held in memory, for a session or window that has been loaded anyway; the SQL aggregate is for ranges wide enough that materialising the sets would be wasteful. Both halve *each set* before summing, so the truncation matches figure for figure — `MuscleVolumeParityTest` pins that, and an edit to either rule has to change both.
- **Attributed volume is not conserved, and the 17-row taxonomy sharpens that.** A secondary link takes a flat 50% however many secondaries the exercise has, so a 1-primary/9-secondary movement attributes 5.5x the volume actually lifted, against 2x for a bench press. The figures therefore track a muscle against itself over time; they are not a share-of-effort split, and no consumer should render them as parts of a whole.

| `PersonalRecordDao.getRecordsPage` | `personal_record(achieved_at)` for the page, `(exercise_id, achieved_at)` for the improvement, **and its query shape** - see below |
| `ExerciseDao.getAllMuscleGroupLinks` | `exercise_muscle_group(exercise_id, muscle_group_id)` (the composite primary key) |
| `BodyMeasurementDao.getAll` / `getLatest` | `body_measurement(created_at)` |

`LargeHistoryBenchmarkTest` seeds a power-user history (10k sessions, ~30k session exercises, 100k sets, 10k personal records) and asserts each of these stays under 500 ms. The budget is generous on purpose: it catches a dropped index turning a join quadratic, not micro-regressions. It is also a figure for an idle development machine, as is every measurement in this section: the test times a fixed piece of SQLite work before each attempt and scales the budget by how much slower than the reference that ran, so the same guard holds on a slow, busy CI runner, and a query gets three attempts so that a spike landing on it alone does not fail the build. Unbounded reads (`getHistoryByExercise`, `getAll`) keep a `PagingSource` variant - screens should use it and leave the `Flow<List<...>>` form to charts and exports.

**The weekly series deliberately have no index on `completed_at` behind them.** `workout_session` carries none, so both series scan that table — and that is the right trade: it is one to two orders of magnitude smaller than `workout_set` (10k rows against 100k at the benchmark's stress scale), and the `GROUP BY` is on a computed expression an index could not serve anyway, so all one would buy is pruning the range filter. Since `getVolumeByWeek` now filters on the session rather than the set, it drives from `workout_session` too and reaches sets through the FK indexes; at the stress scale it measures 40 ms against a 500 ms budget. If session counts ever reach set counts, add the index and a migration with it.

**Page first, then do the work.** `getRecordsPage` reads a window of the records list and, for each row, the record it beat. Written the obvious way that figure is a `LAG` window function over `personal_record`, with `LIMIT`/`OFFSET` applied outside it - which means every page windows and sorts the entire table to return twenty rows, and the outer `ORDER BY achieved_at DESC` can no longer be served by the `achieved_at` index. It measures 22-28ms a page against the stress fixture and gets slower for as long as the user keeps training. Cutting the page *first* - filter, order and limit against `personal_record` alone in a derived table, then join and look the previous record up per returned row with a correlated subquery on `(exercise_id, pr_type)` - measures 1-5ms and, more to the point, measures the same at offset 9,900 as at offset 0. SQLite will not flatten a subquery carrying a `LIMIT` into an outer query that is a join, so the derived table is guaranteed to be cut before the joins see it. `LargeHistoryBenchmarkTest` holds all three shapes (first page, deep page, filtered page).

**An index is not always the whole story.** `getHeadlineRecords` picks one record per exercise, which needs a per-exercise "best" and cannot be served by an index alone: its preference order leads on a `CASE` over `pr_type`, and a sort whose leading key is an expression builds a temporary b-tree however the table is indexed. What decides its cost is therefore *how many times that sort runs*. Written the obvious way - a subquery correlated on the outer row - it runs once per record and measures **1,263 ms** on the fixture above; driven from `SELECT DISTINCT exercise_id` it runs once per exercise and measures **6 ms**. The benchmark is what holds it there, so treat the query's shape as load-bearing rather than stylistic, and re-measure rather than reason about it if you rewrite it.

## The in-progress session draft

The database is not the only thing the app writes. A workout in progress also has a **draft** - `ActiveSession` in `:core:domain`, encoded by `ActiveSessionFormat` as a single JSON document - saved so a process kill does not cost the user their place in the session. It is deliberately outside the schema: it is a snapshot of a screen, not a record of a workout, and it is written far too often to be worth a migration ladder.

- **It overlaps the rows rather than replacing them.** The sets are in `workout_set` either way; the draft is what carries the parts no column holds - the sets half-typed and not yet ticked, how long the session has spent paused, and the rest countdown. Where a draft entry has an id it names the row it came from, so a restore updates rather than duplicates; where the id is null the entry exists only in the draft.
- **`currentExerciseIndex` is the exercise the rest belongs to, and `null` the rest of the time.** It records which exercise the user was on, and for most of the active session screen there is no answer: every exercise of the workout is on the page and every one of them takes sets, which is what makes a superset loggable. Between two sets there *is* one — the user has just logged a set on an exercise and is about to log another — so a draft written mid-rest names it, and a restore reads the rest sheet's "up next" back off it. A rest opened from the session clock follows no set and names nothing, which is why "none" is `null` and not `0`: zero is the first exercise, and a restore would credit the rest to it. A document written while the field was a plain integer still decodes; its `0` on a workout with no exercises names nothing either. Each exercise's half-typed set is restored from that exercise's own trailing incomplete `ActiveSet` either way.
- **Losing it costs a place, never a set.** Every consumer treats an unreadable draft as no draft, which is why `InProgressSessionRepository.load()` returns `null` for a corrupt document as readily as for an empty store, and why nothing here up-converts.
- **The document carries its own version**, outside the session object, for the reason the export envelope does: a draft written by a build that laid the fields out differently is refused rather than misread. Adding a field with a default does not need a bump - `encodeDefaults` and `ignoreUnknownKeys` make that survivable in both directions.
- **It carries the superset grouping too.** `ActiveExercise.supersetGroup` mirrors the column, because the grouping is read on every logged set - it decides whether a rest is due yet (`ActiveSession.isRestDueAfter`) - and an exercise added to a running session may have no row to read it back from. Adding it needed no format bump, per the point above.
- **The rest timer is persisted as an absolute deadline**, epoch millis UTC, never as a remainder. A remainder is stale the instant it is written; a draft reloaded ten minutes later must restore a rest that is *over*. `RestTimerSnapshot` holds the deadline and does the conversion, so `RestTimerState` and `RestTimerController` stay free of any notion of an absolute instant. A paused rest is the exception and is stored as its remainder, which does not go stale. Pausing the *session* is a different question and does not pause the rest: the session clock measures how long the user has been working out, the rest measures how long they have been standing still, and only the first is suspended by a pause.
- **The wall clock, not `elapsedRealtime()`.** `SystemClock.elapsedRealtime()` is the only Android elapsed-time reading that counts device sleep, but it resets to zero on reboot, which makes a persisted deadline meaningless afterwards. For a rest measured in minutes, persisting the wall-clock deadline and letting a reboot read as "the rest is over" is the better trade.
- **What `:core:data` owes on top of the interface:** `save` must be atomic. It is called on every logged set, so a kill landing inside a write is not a remote possibility, and the failure mode is a truncated document. A write-then-rename, a DataStore commit or a single-row transaction all satisfy it; a `File.writeText` over the live document does not.
- **Who writes it.** `ActiveSessionViewModel` is the only writer, and it saves after every
  change — a field edited, a set logged, an exercise opened, a pause. Reading it back is the same
  screen's job on open, and a draft naming a *different* session is left alone rather than
  cleared: at most one session runs at a time, so that means the screen was opened on a session
  it should not have been, and deleting somebody's place in a workout to tidy up is the worse of
  the two mistakes. Clearing it belongs to the two use cases that end a session —
  `FinishSessionUseCase` and `DiscardSessionUseCase` — because the draft's lifetime is the
  session's, and a second closer that forgot it would be a bug nobody sees until the next launch.
- **How it is stored today:** `InProgressSessionRepositoryImpl` writes `in-progress-session.json` in the app's private `filesDir`, via write-then-rename - the bytes go to a `.tmp` sibling, are forced to disk with `FileDescriptor.sync()`, and are then moved onto the live document with `ATOMIC_MOVE`. The scratch file is a sibling rather than a cache-directory file so the move stays a rename within one filesystem; `ATOMIC_MOVE` across mount points degrades into a copy, which is the thing this is avoiding. Concurrent savers serialise on a mutex, since they share the one scratch path. A leftover `.tmp` from a save that was killed mid-write is harmless: nothing reads it, the next save truncates it, and `clear()` removes it.

Restoring on relaunch is *not* alerting. Nothing reads a database while the process is dead, so a rest that ran out while the app was gone comes back `Finished` without ever having rung. Alerting at the deadline needs an OS-scheduled wake-up (`AlarmManager` plus a notification) and is not built yet.

## The half-built template draft

The second thing outside the schema, and the same kind of thing for the same reasons - `TemplateDraft` in `:core:domain`, encoded by `TemplateDraftFormat`, written by `TemplateDraftRepositoryImpl` to `template-draft.json` in the app's private `filesDir`. It is what stops a process kill costing somebody the template they were in the middle of building (#183).

- **It replaces nothing, because there is nothing to replace.** This is where it differs from the session draft, which overlaps rows that exist either way. A template is written *whole* on SAVE - `UpdateTemplateUseCase` replaces the exercise list wholesale - so until the button is pressed, the plan is nowhere at all. That is what makes it the most expensive thing on any screen in the app to lose: several exercises, their sets and their figures, and no row anywhere carrying any of it.
- **Saved instance state would not have been enough**, which is the point worth writing down. A `Bundle` survives the process; it does not survive the task record going with it - a swipe out of Recents, a reboot, a long enough absence. That is an acceptable lifetime for *where the user was* and not for *what they built*, so the editor uses both mechanisms deliberately: the plan here, and the naming dialog, the discard confirmation and the outstanding picker request in the `SavedStateHandle`.
- **It is a slot, not a collection.** At most one template is being edited at a time, because the editor is one destination. `TemplateDraft.templateId` says which - `0` for one that does not exist yet - and an editor opened on a different template ignores what it finds and takes the slot for itself. A draft is cleared the moment its editor is clean, saved or discarded, so a stale one cannot be restored over the next template opened.
- **The figures are text, and the unit travels with them.** Every weight in the editor is *what the user typed*, in the unit in force when they typed it, which is why `TemplateDraftSet.weight` is a `String` and `TemplateDraft.unitSystem` is on the document. A draft restored after the setting changed keeps its own unit rather than being reformatted under somebody mid-edit; the parse happens on SAVE, once.
- **The keys are saved with it.** A line added since the last save has no stored `template_exercise.id`, so the editor hands out negative keys counting down from -1 and set keys counting up from 1. Restoring winds both counters past what the draft already holds; a counter that started over would hand out an identity the plan is already using, and a keystroke would land in two rows.
- **The same file handling as the session draft**, and literally the same code: both go through `AtomicDocument` in `:core:data` - write to a `.tmp` sibling, `FileDescriptor.sync()`, `ATOMIC_MOVE` onto the live document, with concurrent writers serialised on a mutex because they share the one scratch path. The two drafts had the same thing to get right and now get it right once.
- **It is cleared by a wipe and by an import**, alongside the session draft and for the same reason: it names a `templateId` that is about to stop existing, and a draft left behind would be restored over whatever takes that id next. See `LocalDataRepositoryImpl.deleteAll` and `ImportUseCase`.

## Saved instance state, and where it stops

Everything above outlives the process *and* the task. Saved instance state is the fourth lifetime the app uses and the shortest of the durable ones: it survives the process being killed under a backgrounded app, and it goes when the task record does - a swipe out of Recents, a reboot, a long enough absence. #183 is the pass that decided, screen by screen, which state belongs in it.

The rule the audit settled on, and the one to apply to any screen added later:

| The state is… | Where it goes | Why |
| --- | --- | --- |
| transient UI, owned by a composable - a scroll offset, an expanded section, a dialog's own text field | `rememberSaveable` | Compose already carries it into the same `Bundle`, and hoisting it into a ViewModel to save it would be moving state away from what draws it for no gain |
| a ViewModel's own - a search box, a selected tab, a filter, an open dialog, a half-typed form | `SavedStateHandle`, through `savedScreenState` in `:core:ui` | it outlives the process, dies with the task, and none of it is worth a file |
| something the user would call **their work** | a repository | a `Bundle` that a low-memory kill can still lose is not where minutes of somebody's effort belong - see the two drafts above |

- **`savedScreenState` is the one mechanism.** A ViewModel's `MutableStateFlow(ScreenState())` becomes `savedStateHandle.savedScreenState(viewModelScope) { ScreenState() }` and nothing else about the class changes. The state class is `@Serializable`; the fields that must *not* come back are `@Transient` beside the field they are about, which is where the reasoning for each one is written down.
- **What is always `@Transient`:** a write in flight (the process that was making it is gone, and a form restored inert never takes another tap), a one-shot message (it is about something the user was told before they put the phone down), and a permission request (it belonged to an activity that no longer exists, and re-raising it is the second prompt Android answers with the refusal from the first).
- **What must never be saved at all:** rows a query can re-read. A list of a thousand sessions or a workout's worth of typed sets in a `Bundle` is how a screen earns a `TransactionTooLargeException` - the limit is on the *whole* of a task's saved state, not on one screen's share of it. The active session screen is the sharpest case: its entries go to the workout draft, and only the rename field and the corrections typed over already-logged sets go to saved state.
- **The encoding is a JSON string**, not a `Parcelable` or `androidx.savedstate`'s serialization. The state classes are already reachable by the `kotlinx.serialization` plugin every feature applies for its route types, and a `String` is something a `SavedStateHandle` holds with no Android framework behind it - so the same JVM test that drives a ViewModel can drive its restoration. `SavedScreenStateTest` covers the mechanism; each screen's own suite covers its state.
- **A restored state has to reach the first frame.** Most screens assemble `uiState` with `combine(...).stateIn(...)`, which holds its first emission until every read has answered - so an `initialValue` built from nothing would draw an empty search box and a closed sheet for that whole window and then put them back. Where that was visible, `initialValue` is built from the restored screen state instead.

## The user preferences store

The fourth thing the app writes, after the schema and the two drafts: the user's settings - `UserPreferences` in `:core:domain`, held in a **Preferences DataStore** at `user-preferences.preferences_pb` in the app's private storage, implemented by `UserPreferencesRepositoryImpl`.

Outside the schema for the same reason the drafts are, from the other direction. A setting is not a record of anything that happened; it is a single-valued fact that is read on the way to the first frame of nearly every screen and written a handful of times in a device's life. A one-row table would buy a migration ladder for a document with six scalar fields and put a database read in front of the first render.

| Key | Type | Default |
| --- | --- | --- |
| `unit_system` | `UnitSystem` name | `METRIC` |
| `theme` | `ThemePreference` name | `SYSTEM` |
| `default_rest_duration_seconds` | int64 seconds, 1 to 86 400 | 180 |
| `bar_weight_milligrams` | int64 milligrams, 1 to 10 000 000 000 | 20 000 000 (a 20 kg Olympic bar) |
| `plate_inventory_milligrams` | string, `<weight>x<pairs>` entries joined by `;` (`20000000x2;10000000x2`) | absent — the standard rack for `unit_system` |
| `training_goal` | `TrainingGoal` name | `STRENGTH` |
| `fitness_level` | `FitnessLevel` name | `BEGINNER` |
| `custom_rep_range_min`, `custom_rep_range_max` | int32 reps, both ends inclusive | absent — `8` and `12`, the hypertrophy range; one without the other reads as absent |
| `custom_increment_milligrams` | int64 milligrams, 1 to 10 000 000 000 | absent — twice the smallest plate on the user's rack |
| `one_rep_max_formula` | `OneRepMaxFormula` name | `EPLEY` |
| `onboarding_completed` | bool | `false` |
| `notifications_<kind>` | bool, one key per `NotificationKind` | `true` for `rest_timer`, `false` for the rest |
| `notification_permission_requested` | bool | `false` |
| `reminder_days_iso` | string, ISO day numbers comma-separated | `1,3,5` — Monday, Wednesday, Friday |
| `reminder_time_minutes` | int32 minutes after midnight | 1080 — 18:00 |

- **Preferences DataStore rather than Proto.** Proto would add the protobuf plugin, a `.proto` file and a generated-source directory for six scalars, and the typed document it buys is largely spent again: `UserPreferences` is declared in `:core:domain` where the storage layer cannot reach it, so a mapping step exists either way. Preferences also degrade *per key* where a serialized document is all-or-nothing, and `edit` over one key is a narrower write than `updateData` over a whole document - a new setter physically cannot clobber a sibling by forgetting to copy it through.
- **Key names and enum names are a persisted format.** Renaming `unit_system`, or renaming `UnitSystem.METRIC`, silently resets that setting for every existing install. `UserPreferencesTest` pins the enum names for exactly this reason; the keys are string literals in one private object rather than derived from anything a refactor would rename.
- **Units are canonical, as everywhere else.** `bar_weight_milligrams` is milligrams because it is added to and subtracted from set weights, and `unit_system` decides only how a number is *rendered*. Nothing in the store is written in the user's display units - see the note under [Storage assumptions](#storage-assumptions).
- **Every read falls back to the default, three times over.** A key that is absent (a fresh install), a key holding an enum name this build does not have (a downgrade, or a value since renamed), and a key holding a number the model refuses (a rest outside one second to a day, a bar weight or custom increment outside one milligram to ten tonnes, which no setter would have written) all produce the documented default rather than an exception, and an unreadable store produces a whole default object. A settings read is on the path to the first frame; it must not be the thing that throws. Rejection happens on the *write* side, where `require` refuses a bad value before it can be stored.
- **Emissions are `StateFlow` semantics over a file.** `observe()` delivers the current settings to every new collector immediately, without a write having to happen, then re-emits on change - conflated, latest-wins, and silent when a write changes nothing. That is the contract `SessionStateRepository` documents, and the screens depend on it: `observe().first()` has to return on a fresh install.
- **The rest duration is stored to the second.** A value finer than that is truncated on the way in, which is the resolution a rest timer is set in anyway - except one that would truncate to *zero*, which is rejected rather than stored, since the reader would then discard it for the default and the setting would silently not take.

**The store is part of the export envelope**, under a top-level `preferences` object, and is restored last. This reverses what this file said while nothing consumed the store: a restore is meant to reproduce a *device*, and `unit_system` in particular changes how every stored weight is read back, so leaving it out would hand somebody their history in units they do not lift in. Restoring it after the tables means the app re-themes and re-formats once, at the end, rather than mid-write. What is still out is the in-progress draft, for the reason the section above gives - it is a snapshot of a screen, not a record of a workout. See [export-schema.md](export-schema.md).

## The auto-backup schedule store

The fifth thing the app writes, and the smallest: whether the weekly automatic backup (#181) is on, when it last wrote a file, and whether the last run gave up - `AutoBackupSchedule` in `:core:domain`, held in a **second Preferences DataStore** at `no_backup/datastore/auto-backup.preferences_pb`, implemented by `AutoBackupRepositoryImpl`.

| Key | Type | Default |
| --- | --- | --- |
| `auto_backup_enabled` | bool | `false` |
| `auto_backup_last_success_at` | int64 epoch millis UTC | absent - never run |
| `auto_backup_last_failure_at` | int64 epoch millis UTC | absent - the last thing to happen was not a failure |

- **A file of its own rather than three more keys in `user-preferences`, and the reason is the export.** The settings store is a user's *answers*, and it is what an export carries and a restore replaces. Two of these three fields are instead a record of what a background job did on *this* device, and the third would be a lie if it travelled: an import writes settings, it does not enqueue work, so a restored `auto_backup_enabled = true` would draw a toggle that is on with nothing scheduled behind it. Sharing the file would also put the schedule inside "delete all data", which clears the settings store wholesale - silently changing a backup schedule the user did not ask it to touch. So **the schedule is not part of the export envelope**, deliberately, unlike the settings. "Delete all data" leaves the toggle and the enqueued work alone, and forgets only the two timestamps (`AutoBackupRepository.forgetRuns`), because it deletes the files they describe.
- **Nor part of Android's own backup**, which is the same argument one step further. A schedule store that travelled to a new phone would land there with `auto_backup_enabled = true` and no work enqueued behind it: a switch drawn on, naming a backup from the old phone, over a job that will never run. So it lives in `no_backup/`, beside WorkManager's own database, which is what keeps the flag and the work one fact. Nothing else the app persists travels either any more - [Android's own backup](#androids-own-backup) excludes it by name - but that is a list somebody has to remember to add to, and this store is exempt by the directory it is in. Two guarantees, and the weaker one does not need the stronger one to be right.
- **A success clears the failure; a failure keeps the success.** "The last run failed" and "there is a backup from three Sundays ago" are different pieces of news and the backup screen shows both - the first says something is wrong, the second says how much it has cost. A later success supersedes the failure it follows, which is what makes `AutoBackupSchedule.hasFailed` a null check rather than a comparison of two instants.
- **Read like the settings store, written like it.** `observe()` carries the same emission contract (current value on subscribe, never empty, never failing at the collector - an unreadable store draws a toggle that is off, which is the safe direction for a screen that has to put something under the heading) and the writes carry the same asymmetry, throwing. A timestamp at or before the epoch is not an instant this app wrote, so it reads as "never" rather than as a date in 1970.
- **Except for `read()`, and the worker is the reason it exists.** The flow's fallback is right for a screen and wrong for the job that acts on the flag: to the worker, "the user turned it off" and "the store could not be read" are the difference between a week correctly skipped and a week silently lost. Reading through `observe()`, a transient IO error at three in the morning would look exactly like the toggle being off - the run reports success, writes no file, asks for no retry, records no failure, and the row goes on showing the previous week's date. So `AutoBackupRepository.read()` is the same value fetched once with no fallback beneath it, throwing `IOException` instead, which puts that run into the same retry-then-report path as a failed write. Screens must not call it.
- **The files themselves are not in either store.** Auto-backups are written to `backups/` in app-specific storage - the same directory the manual export uses, resolved for both by one `BackupDirectory` (see "Where the backup files live" below), distinguished by name: `titan-auto-<yyyy-MM-dd>.json` against the manual `titan-backup-<yyyy-MM-dd-HHmm>.json`. Retention keeps the three most recent *automatic* ones and never touches a manual export; it also deletes the `titan-auto-*.json.tmp` scratch file a killed run leaves, and only those, since the manual export's scratch file may be one the screen is writing at that moment. Retention runs only as part of a backup, so **turning the schedule off keeps the backups already written** until uninstall or "Delete all data", and the backup screen says so beside the toggle. **"Delete all data" empties the directory**: every manual export, every automatic backup and every `*.json.tmp`, in every `backups/` that `AutoBackupFiles.everyDirectory` names, through the same `BackupDirectory` (both roots, so a backup written to the internal fallback while no external volume was mounted is found too), and its dialog says so. The stamp is to the day so a retried run overwrites its own file rather than pushing an older backup out of the window. That directory is **deleted on uninstall**, which is why the backup screen says so next to the toggle: an automatic backup does not survive a reinstall, and the manual "save a copy" is what exists for that case. It is deleted rather than restored because the rules below exclude it - both of its possible roots are backup domains like any other, so without that line a reinstall would quietly bring last month's backups back and the sentence on the screen would be false.

## Where the backup files live

Every backup file, manual or automatic, is under one `backups/` directory, and one place decides where that is: `BackupDirectory` in `:core:domain`, implemented by `AppBackupDirectory` in `:core:data` and bound as a singleton. `AutoBackupFiles` (the weekly backup, its retention, and "Delete all data") and `BackupViewModel` (the export, "Save a copy…" and the share) both ask it, which is what a port buys a feature that may not depend on `:core:data`.

| Android | Root | Why |
| --- | --- | --- |
| 8 to 10 (API 26-29) | `filesDir` | The external files directory, `Android/data/app.titan.gym/files`, is readable and writable there by any app holding `READ_`/`WRITE_EXTERNAL_STORAGE`, on Android 10 by one in legacy storage mode. A backup is the whole history and the body log in plain JSON, and a file the restore trusts (#259). |
| 11 and later | `getExternalFilesDir(null)`, or `filesDir` when there is no external volume | The platform scopes the directory to the app, and it stays reachable over USB and listed under the app in the storage screen. |

- **Below Android 11 a backup leaves the app only through it.** No file manager can browse `filesDir`, so the backup screen's "Save a copy…" (the system document picker) and "Share" (the `FileProvider`, whose `file_paths.xml` declares `backups/` under both roots) are the ways out. Both act on the export the screen has just written, so an automatic backup there cannot be taken off the phone at all; it is a local snapshot, and "Export a backup" is the copy that travels.
- **Files under the other root are moved on first use.** The first `resolve()` in a process moves every finished `titan-*.json` from the other root's `backups/` into the chosen one, keeps the copy already in place when both have a name, deletes the `titan-*.json.tmp` scratch files an interrupted export left, and removes the old directory if that empties it. It covers an install upgraded from a build that wrote to shared storage on Android 8 to 10, and a phone upgraded to Android 11 with its backups in `filesDir`. A backup larger than `ExportFormat.MAX_DOCUMENT_BYTES` is not moved, since no restore would read it and below Android 11 the old directory is one other apps can write to; it stays where it is, unreported, until "Delete all data" or an uninstall. Once per process, idempotent across processes, and a file that will not move is retried by the next process; it never fails the caller. On first use rather than at startup, because every reader and writer asks the resolver first and a startup hook would put the listing, and on an old phone the copy, on every cold start. The move crosses filesystems on most devices, so it falls back from `renameTo` to a copy into a `.tmp` sibling, a rename, and only then the delete.
- **Both roots are excluded from Android's own backup**, below.

## Android's own backup

Everything above is about what the app writes. This is about what the **platform** does with it behind the app's back, which until #180 was: upload all of it to the user's Google Drive, and restore it on reinstall before the first frame.

`android:allowBackup` stays `true`, and two rule files say what may be taken. Both are referenced from `<application>`, and the platform reads exactly one of them:

| File | Read by | Covers |
| --- | --- | --- |
| `app/src/main/res/xml/data_extraction_rules.xml` | Android 12+ (`android:dataExtractionRules`) | cloud backup and device-to-device transfer, configured separately |
| `app/src/main/res/xml/backup_rules.xml` | Android 11 and below (`android:fullBackupContent`) | the one channel those versions have |

What they exclude is the whole of the app's durable footprint:

| What | Where | Rule |
| --- | --- | --- |
| The database and its journal sidecars | `databases/titan.db`, `-wal`, `-shm`, `-journal` | excluded by name |
| The settings store | `files/datastore/user-preferences.preferences_pb` | the `datastore` directory is excluded |
| The in-progress draft and its scratch file | `files/in-progress-session.json`, `.json.tmp` | excluded by name |
| The half-built template draft and its scratch file | `files/template-draft.json`, `.json.tmp` | excluded by name |
| Exported and automatic backups | `backups/` under `files/` below Android 11 or when there is no external volume, under the external files directory otherwise | the directory is excluded in both domains |
| The auto-backup schedule | `no_backup/datastore/auto-backup.preferences_pb` | no rule needed - `no_backup/` is exempt by the platform |

- **Excluding the files rather than setting `allowBackup="false"`.** Off wholesale is the safe-looking option and it is the worse one. It throws away device-transfer for anything that *should* travel - nothing does today, but `no_backup/` is where non-durable state goes and that boundary only means something while the mechanism exists - and an app that opts out of backup entirely reads, to a store reviewer, as one with something to hide. The exclusion list gets the actual guarantee: **the user's training history leaves this phone only in an export file they asked for**.
- **Which is a claim the app makes in words, and was not keeping.** Settings reads "No account. No cloud. Everything stays on this phone" and the export screen "nothing leaves the phone until you do". Under the platform default both were false. They are true now, and they are the reason a change to these files is a change to what the app promises rather than a configuration detail.
- **Both files, always.** The platform picks one by version and ignores the other, so an exclusion written in only one is a hole that opens on Android 11 and below and on no device anybody tests. `BackupRulesTest` asserts the two lists are identical, and asserts each against the paths the code actually writes.
- **Cloud and device-transfer are excluded identically.** They are configured separately, and it is tempting to allow the transfer: it is a phone the user is holding either way. But a transfer that restores a database onto a device whose owner is also restoring an export file is the same collision as the cloud case arriving by a different road, and #37's restore has no way to know it happened.
- **The sidecars are named for a reason of their own.** `-wal` and `-shm` are backed up as separate files with nothing guaranteeing they are consistent with the `.db` they came from. Excluding the database and not its sidecars would be worse than excluding neither: a `.db` restored beside a mismatched `-wal` comes back *corrupt*, where the whole set comes back merely stale. `-journal` is the fourth name for the same reason: Room's journal mode is `AUTOMATIC`, which is WAL on most devices and `TRUNCATE` on a low-RAM one, where the sidecar is a rollback journal under that name.
- **`backups/` is excluded twice because it has two homes.** `BackupDirectory` puts it under `files/` on Android 8 to 10 and on a device with no external volume mounted, and under the external files directory otherwise; `file_paths.xml` declares a `FileProvider` path for each. Excluding only the `external` copy would leave a whole export, every session the user has logged, on Drive from every Android 8 and 9 phone. Those versions read `backup_rules.xml`, which is why the `file` line has to be in both files.
- **A restore cannot be declined.** It lands before first launch, with no prompt - which is why none of this can be handled by asking the user at the time, and why it had to be settled before #37's explicit restore shipped rather than alongside it.
- **The paths in that test are the production constants, not copies of them.** A list of literals sitting next to the rule files would assert that two hand-written things agree and nothing more: rename `DATABASE_NAME`, or the in-progress draft, or the backup directory, and the rules would stop matching anything while every test stayed green. So `BackupRulesTest` reads `DATABASE_NAME`, `DATASTORE_DIRECTORY`, `InProgressSessionRepositoryImpl.DOCUMENT_NAME`/`.SCRATCH_NAME` and `BackupDirectory.NAME` and derives the database's sidecars from the database's own name, which is how SQLite derives them. Those constants are public for this reader alone. The one name it cannot reach that way is covered separately: the `datastore` directory belongs to DataStore rather than to this app, and `UserPreferencesStoreLocationTest` pins the constant to what `preferencesDataStoreFile` actually does. The backup directory has one spelling, in the domain port every writer resolves it through.
- **Anything new the app persists goes in both files.** A second Room database, a third DataStore, a cache written under `files/` - none of them fail a build by being absent here, and the symptom is a user's data on Google's servers with nothing visible until a reinstall writes a stale copy over a live one. `BackupRulesTest`'s list of paths is the checklist; it fails when the files disagree with it. Renaming something already on the list is the case it now catches by itself; *adding* one is still a thing somebody has to remember.

Verifying it is a device job, not an XML review: on a phone signed in to a Google account, log a session, `adb shell bmgr backupnow app.titan.gym`, uninstall, reinstall, and confirm the app opens at onboarding with nothing logged. `adb shell dumpsys backup` shows the app registered with the excluded files absent from its backup set.

## Implications for backup and import/export

The format itself is specified in [export-schema.md](export-schema.md); what belongs here is what the *schema* obliges it to do.

- The export envelope must carry the schema version it was written at. An import reads it and refuses (or up-converts) anything it does not understand - the Room migration ladder only upgrades a *database file*, not a JSON document.
- Units are integers and timestamps are epoch-millisecond UTC, so no locale or precision conversion belongs in the serializer; converting to kilograms, pounds or local time is a UI concern.
- Restoring by replacing the database file is only safe when the file's version is one the app can migrate; prefer a row-level import that goes through Room.
- Enum-like columns, set bounds, dense set numbering, the superset rules and `body_measurement`'s all-null rule are the domain's invariants and not the schema's, so an importer has to decide what to do about them. What this app's importer decides is to **preserve them verbatim** and refuse only what SQLite itself would refuse, plus the few ranges the format itself defines (ids, timestamps, set numbering and RPE, at most one session in progress, and well-formed text in every text column a unique key covers) - a value from a newer version is a record rather than a corruption, exactly as the `achievement` and `collected_item` bullets require. The readers survive a preserved value outside the domain's bounds instead. That decision, and the ranges, are argued in [export-schema.md](export-schema.md), not here.

**"Match on natural keys and remap ids" is a rule about a *merge*, and this app's import does not merge.** It wipes every table and re-inserts the document, so the file's ids are the only ids afterwards and every foreign key in it still resolves to the row it was written against; remapping would buy nothing and would need a conflict rule per table. The same goes for the reference data: the 17 muscle groups and 9 system tags are carried in the file and restored from it rather than resolved by name against the target install, because the seed is *not* replayed during an import - replaying it would leave every seeded row the file does not contain still in the table. A future consumer that does merge - a sync - is back under the original rule, which is why it is stated rather than deleted.
